# Solicitar inclusão em um time

Esta página explica como pedir para ser adicionado(a) ao seu **grupo (time)** na
organização **`ELT73A-S22-2026-2`** do [GitHub](https://github.com/).

Toda solicitação é feita abrindo uma **issue** em um repositório dedicado, por meio
de um formulário. Depois de enviada, um administrador adiciona você ao time e fecha
a issue.

:::info[Pré-requisitos]

- Ter uma conta no [GitHub](https://github.com/).
- Saber o **slug do seu grupo** (de `grupo-a` até `grupo-j`).
- Conhecer o seu **username** do GitHub (o nome que aparece no seu perfil, sem o `@`).
  :::

## Passo a passo

### 1. Abra o formulário de solicitação

Acesse o repositório de solicitações e clique em [New issue](https://github.com/ELT73A-S22-2026-2/elt73a-central/issues/new/choose) (Nova issue), ou use
o [link direto](https://github.com/ELT73A-S22-2026-2/elt73a-central/issues/new?template=solicitar-time.yml):

```
https://github.com/ELT73A-S22-2026-2/elt73a-central/issues/new?template=solicitar-time.yml
```

### 2. Selecione o formulário

Na tela de escolha, selecione **"Solicitar inclusão em time"**.

### 3. Preencha os campos

| Campo                      | O que informar                                          |
| -------------------------- | ------------------------------------------------------- |
| **Grupo (slug do time)**   | Escolha o slug do seu grupo, de `grupo-a` a `grupo-p`.  |
| **Seu username do GitHub** | Seu nome de usuário, **sem o `@`**. Ex.: `octocat`.     |
| **Confirmação**            | Marque a caixa confirmando que o username está correto. |

:::caution[Confira o username]
Um username digitado errado impede a inclusão e atrasa o processo. Confirme no seu
perfil antes de enviar.
:::

### 4. Envie e aguarde

Clique em **Submit new issue**. Pronto — agora é só aguardar. Um administrador irá:

1. Verificar o grupo e o username informados.
2. Adicionar você ao time correspondente.
3. Fechar a issue confirmando a inclusão.

:::tip[Como saber que deu certo]
Quando a issue for **fechada**, você já deve constar como membro do time. Você também
recebe uma notificação por e-mail convidando para a organização/time — aceite-a se
solicitado.
:::

## Como confirmar que você está no time

Acesse a página de membros do seu grupo, trocando `<slug>` pelo seu grupo:

```
https://github.com/orgs/ELT73A-S22-2026-2/teams/<slug>/members
```

Por exemplo, para o `grupo-a`:

```
https://github.com/orgs/ELT73A-S22-2026-2/teams/grupo-a/members
```

## Dúvidas frequentes

**Errei o username / escolhi o grupo errado. E agora?**
Comente na própria issue com a correção antes de ela ser fechada. Se já tiver sido
fechada, abra uma nova solicitação.

**Não sei qual é o slug do meu grupo.**
Os grupos dos alunos seguem o padrão `grupo-a`, `grupo-b`, … até `grupo-o`
(o `grupo-p` é reservado ao professor). Confirme com o professor ou com o seu grupo qual é o seu.

**Posso pedir para mais de uma pessoa na mesma issue?**
Não. Cada aluno abre a sua própria solicitação, para facilitar o controle.

:::danger[Não é o canal para dúvidas gerais]
Este repositório é **apenas** para solicitações de inclusão em times. Dúvidas sobre
conteúdo, notas ou entregas devem ser encaminhadas pelos canais oficiais da disciplina.
:::

## Uma org por grupo vs. times em uma única org

Para o seu caso (labs `lab00`…`lab10`, templates, PlatformIO/STM32, automação com `gh`), **quase sempre a melhor opção é uma única organização com times (Grupo-A, Grupo-B, …)**.

---

### Comparação rápida

| Critério                  | **1 org por grupo** (`ELT73A-S22-2026-2-A`, …) | **1 org + times** (`ELT73A-S22-2026-2` + `grupo-a`) |
| ------------------------- | ---------------------------------------------- | --------------------------------------------------- |
| Isolamento entre grupos   | Muito forte                                    | Bom (repos privados + permissão só do time)         |
| Administração             | Pesada (N orgs)                                | Simples (1 org)                                     |
| Criar labs em massa       | Script por org ou loop em N orgs               | Um loop só, mais simples                            |
| Templates                 | Org de templates à parte ou copiar N vezes     | Um `lab00-template` na mesma org                    |
| Times / membros           | Cada org tem seus membros                      | Times nativos + membership fácil                    |
| Visão do professor        | Trocar de org o tempo todo                     | Tudo num só lugar                                   |
| Limites do GitHub         | Risco de bater limite de orgs / convites       | Bem mais confortável                                |
| Billing / settings        | Repetir política N vezes                       | Configurar uma vez                                  |
| Autograding / CI          | Disperso                                       | Centralizado                                        |
| “Aluno não vê o outro”    | Natural                                        | Com repo privado + só o time no repo, também ok     |
| Complexidade para o aluno | URLs longas, várias orgs                       | Um padrão: `lab00-grupo-a`                          |

---

### Uma org por grupo

**Vantagens**

- Isolamento máximo (um grupo não “existe” na org do outro).
- Cada grupo pode ter settings próprios (se um dia precisar).
- Modelo parecido com “cada time = uma conta/org”.

**Desvantagens**

- Muitas orgs para criar, convidar alunos e manter.
- Scripts e docs ficam mais longos (`ELT73A-S22-2026-2-A/LAB05`, …).
- Template costuma ficar em outra org (`ELT73A-LAB-TPL`) e o fluxo `--template` / permissões complica.
- Professor perde visão única (issues, Actions, busca de repos).
- No plano educacional/free, gerenciar dezenas de orgs vira atrito real.

**Faz sentido quando:** grupos são projetos longos, quase independentes, com admins diferentes, ou há requisito formal de isolamento total.

---

### Uma org + times (Grupo-A, Grupo-B, …)

**Vantagens**

- Um só lugar para templates, labs e projeto.
- Times do GitHub são feitos para isso: membros + permissão em repos.
- Automação simples (`lab00-grupo-a` … `lab00-grupo-x`).
- Aluno clona um padrão fixo; professor lista tudo com um `gh repo list`.
- Fácil conceder `push` só ao time certo.
- README, CI e componentes Docusaurus ficam estáveis.

**Desvantagens**

- Todos os grupos “moram” na mesma org (nomes de repo precisam ser claros).
- Se alguém errar permissão e deixar um repo interno/público demais, o isolamento cai — exige disciplina no script (`private` + team `push` só no repo do grupo).
- Alunos da org podem, em alguns casos, _ver que a org existe_ e listar o que a política da org permitir (repos **privados** de outro time continuam inacessíveis sem permissão).

**Faz sentido quando:** turma de disciplina, vários labs, mesmo professor, automação e templates — **o seu cenário**.

---

### Isolamento de verdade (o que importa na prática)

O que impede o Grupo B de ver o código do Grupo A **não é** “org separada” por si só; é:

1. Repositório **private**
2. Time **só do grupo** com acesso (`push` / `pull`)
3. Alunos **não** serem owners da org
4. Scripts que nunca adicionam o time errado

Com isso, **1 org + times** isola tão bem quanto N orgs para uso acadêmico normal.

---

### Recomendação para ELT73A / S22

| Escolha                  | Recomendação                                                        |
| ------------------------ | ------------------------------------------------------------------- |
| **Padrão da disciplina** | **1 organização** `ELT73A-S22-2026-2` + times `Grupo-A` … `Grupo-X` |
| Repos                    | `lab00-template`, `lab00-grupo-a`, …, `projeto-grupo-a`             |
| Alunos                   | Membros do time; **não** owners                                     |
| Templates                | Na mesma org, marcados como template                                |
| Docs (Docusaurus)        | Componente com abas por grupo, como o `LabTeamMembers`              |

Use **1 org por grupo** só se houver regra institucional de isolamento extremo ou cada grupo for um “mini-projeto” com gestão própria o semestre inteiro.

---

### Resumo em uma frase

**Para laboratórios de uma turma: uma org com times é melhor** — menos trabalho, melhor automação, templates simples e isolamento suficiente com repos privados. **Uma org por grupo** só compensa se o isolamento administrativo total valer o custo operacional.
